## Trusted operation and transaction design

Propose narrow, versioned RPC operations for Manual create/update/complete Save/reopen and Worksheet private create/update/reopen, plus a separate **prepare normalized assessment** operation. Signatures accept the document, request ID, record ID (for update), and expected revision. They do **not** accept a trusted Teacher ID, role, school year, owner, adviser flag, or authorization flag. Supabase's authenticated JWT identity must be derived server/database-side (`auth.uid()` or a separately verified server session). The frontend never holds a service-role key.

Each write is one database transaction/RPC call. In that transaction: derive identity; lock/check the active profile, one official Settings row/year, and one compatible teaching-load tuple; lock/check an existing owned row and source plan when relevant; verify document kind/version and content state; check and lock the unique request receipt; compare expected revision; perform one CAS update or create; store the private result receipt; commit together. Prefer explicit row locks for Settings/profile/assignment/source and a unique receipt key plus row-revision predicate for races. Recheck authorization on distribution in a separate future operation. Incomplete unassigned Worksheet drafts can be private, but any selected subject/grade must match a trusted teaching tuple; an adviser assignment cannot substitute. A missing/ambiguous Settings row fails new writes. Historical owner reads remain allowed; historical edits require a separate Owner decision.

The preparation/materialization operation first applies complete-content validation and then upserts ordered groups, items, and private keys inside **one** transaction, preserving the item UUID mapping and verifying no existing distribution, assignees, or submissions. It never creates `worksheet_sections`, `task_assignees`, notifications, submissions, or score releases. Save/Generate/Reopen/Prepare **must** leave the document student-invisible; actual RLS and grants must prove this in the disposable project. A later explicit distribution RPC must separately validate Teacher load, section/year compatibility, enrollment, content completeness, recipient scope, and Teacher confirmation. Existing score-release authorization remains a separate boundary.

Use a least-privileged function owner with reviewed ownership and no broad `BYPASSRLS` privilege. Propose `SET search_path = pg_catalog, pg_temp` and qualify every `public.*` table and `auth.uid()` function call explicitly; never resolve a security-sensitive relation through the caller's search path. Use no dynamic SQL, and explicitly `REVOKE EXECUTE FROM PUBLIC` and `anon` before narrow authenticated `GRANT EXECUTE` after review. Check the actual definer/RLS interaction in the disposable database; function ownership can bypass RLS. New private tables must have RLS enabled and default-deny direct access. Existing permissive policies are OR-composed; adding a stricter policy alone does not close an ownership-only direct write. Revoke direct `INSERT/UPDATE/DELETE` table **and column** paths for untrusted roles only in a coordinated rollout that preserves both AI and worksheet legacy behavior. Existing RLS, policy definitions, grants, function owners, and Storage settings are **not verified** by TDI-04A.

All fixtures use invented UUIDs and `example.invalid` identities, never copied application records. Each test records synthetic row IDs and before/after hashes or counts for relevant tables. | Cases | Assertions |
| --- | --- |
| M1–M5 Manual lifecycle | New private incomplete draft; exact V2 round-trip; same-ID update; complete Save; same-ID reopen and saved update. Keep AI HTML readable and reject overwrite through Manual RPC. |
| W1–W6 Worksheet drafts | Empty groups, partial questions/choices, absent key/points, private same-ID reopen/resave, preserved group/question order and directions, stable IDs. Incomplete draft cannot materialize or distribute. |
| A1–A7 authorization | Active assigned Teacher positive; inactive/archived, wrong role, forged owner, adviser-only, subject/grade/year mismatch, cross-owner source, missing/ambiguous Settings negative. Verify denied writes leave no rows/receipts. |
| R1–R5 concurrency | Identical create/update retry returns original receipt; conflicting payload same request ID denied; stale/concurrent revision loses; injected mid-transaction failure rolls back document, items, keys, and receipt. |
| H1–H3 history/source | Authorized old-year owner read; old-year edit denied without relabeling; saved owned source required, subject/grade/year compatible. Legacy AI source behavior remains explicitly unresolved until trusted metadata is available. |
| S1–S5 security | Direct table/column write bypass denied; anon and student RPC denied; private answer keys absent from student reads and payloads; unreleased scores inaccessible; Storage bucket/object policies checked only after separately approved metadata access. |
| N1–N4 no side effects | Save, Generate, Reopen, Prepare leave distribution rows, assignees, notifications, submissions, and score releases unchanged. Explicit distribution requires separate authorized action and enrolled recipients. |

Before any fixture, the future harness must screen a separately named project reference and canonical URL, reject the production reference and inherited production credential variables, require an Owner disposable attestation, then obtain an **independent metadata identity observation**. Only after the identity matches may a separately approved read verify a synthetic marker installed in that test project. A caller-supplied name or marker alone is not proof. The [guard](../tools/tdi04/isolationGuard.mjs) encodes this ordering; the [integration CLI](../tools/run-tdi04-integration.mjs) always exits blocked today because no live verifier, migration, or database adapter is installed. The guard currently supports only canonical hosted-project URLs. Local-stack support requires a separately reviewed loopback identity protocol.

For a hosted disposable project, propose a **test-environment-only** sentinel such as `integration_test_environment(marker VARCHAR(128) PRIMARY KEY, purpose TEXT NOT NULL)` with one randomly generated marker and purpose `eduscribe-tdi04-synthetic`. It is not part of the application schema and must never be created in production. The marker read and its setup are future, separately approved database operations. It confirms test provisioning after project identity verification; it does not, by itself, prove project ownership or safety.
